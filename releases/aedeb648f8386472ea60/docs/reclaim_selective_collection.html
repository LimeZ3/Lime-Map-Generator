Selective reclaim collection effort curves

The viewer at data/processed/reclaim_collection_comparison/index.html now shows per-contact collection curves for all 11 existing pilot maps, six delay profiles and contact budgets 1–8. This is an additional diagnostic. Existing route geometry, ownership, objective scores and physical mass are unchanged.

For an entity containing mass m, reference processing rate r=25 mass/s and per-entity acquisition delay d, the collection effort score is q = m / (m/r + d) in mass per engineer-second. Order targets by decreasing q. The vertical axis is the score of the next target, while the horizontal axis can show cumulative mass or cumulative handling work. Equal-mass entities are grouped for display only after their individual overhead is counted.

Each segment amortizes acquisition work across its target's mass. It is not instantaneous output during engine animations, nor an optimal finite-budget collection schedule. A single entity must still be acquired and reclaimed. Engineer travel and actual acquisition timings remain unmeasured. Sorting by this rate disregards spatial visit order, so these curves describe a best-first handling-only opportunity rather than a feasible route between all objects.

The movable rate probe counts all attributed targets meeting q >= threshold, and reports their mass and handling work. The initial 12.5 mass/engineer-s value is an explicit 50%-of-reference diagnostic probe, not a recommended boundary between good and bad stock. There is no automatic cutoff. Dots mark the largest absolute rate decline between adjacent target groups; a details table separately shows the first decline. Neither is automatically a meaningful gameplay knee. The end of a curve is exhaustion of stock, not an artificial zero-rate target. At zero acquisition delay every target has rate 25 and no rate decline exists.

Existing projected own-half entity scope and saved contact territory membership are reused. Tied ownership divides both entity mass and handling work equally; such fractional curves are attributed opportunity, not executable partial-object jobs. Base-preferred and whole-own-pool curves are exported separately; the viewer plots only contacts. Unknown mass remains excluded, with prior warnings retained. Adding low-return objects to a fixed pool does not lower the mass of its existing high-return targets.

Reproduction and validation

Use the existing runtime with PYTHONPATH=src:

.venv-codex/Scripts/python.exe -m supmapai.tools.build_reclaim_effort_curves
.venv-codex/Scripts/python.exe -m supmapai.tools.audit_reclaim_effort_curves
.venv-codex/Scripts/python.exe -m supmapai.tools.compare_reclaim_collection --report

The builder does not rerun extraction or contact searches. Each map exports effort_curves.json and effort_curve_segments.csv, including full boundaries, fractional entity counts, first/largest declines and source/territory hashes. Across 528 saved configurations the exports contain 3432 curves and 26132 segments. Independent audit verifies source hashes, route/base/all-pool mass/count/work parity, fractional conservation, per-entity equations, monotonic rates, continuity, decline boundaries and CSV/JSON parity. All 163 targeted tests pass, including eight selective-curve tests. Browser QA covers all maps, all six profiles, contact budgets, both axes, rate controls and first-decline details. No model thresholds, hosted deployments or collection reruns changed.

Comparing nonzero overhead assumptions

The default viewer now compares0.5/1/2s, with the already-computed zero-delay case retained only in optional controls/all profiles. No new zero-delay contact search was run for this UI change. It remains a numerical validation baseline. For a fixed entity pool all positive delays order targets identically, because q_d=25m/(m+25d) is strictly increasing with mass. Every entity-group boundary therefore occurs at the same cumulative mass, though handling-work coordinates change. However, rate changes are nonlinear: q_2=q_0.5/(4-3q_0.5/25). Small objects lose proportionally more rate than large ones. Absolute thresholds and the largest absolute rate decline need not select the same stock.

Tabula K4 has exactly identical entity masses and ownership shares in both profiles. F1's largest drop stays after3375.36 mass; F3's stays after5659.2. F4's largest-drop boundary moves2026.08->1209.6. At the same12.5 mass/engineer-s probe, F3 qualifying mass falls5659.2->4752.0, and F4 falls2026.08->1209.6. Thus good-core-versus-tree-tail conclusions are robust here, but exact good-mass amounts and largest-drop knees are delay-dependent. The whole library profiles also reoptimize contacts and may change ownership, so they are not uniformly fixed-pool rate-rescaling comparisons. No delay is physically calibrated yet.
