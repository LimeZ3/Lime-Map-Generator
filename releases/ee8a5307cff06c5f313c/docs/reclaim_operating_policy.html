Reclaim operating policy

The user fixed the operating settings after the sensitivity study:

  • One acquisition overhead: 1 second per entity.
  • Three map-relative groups: Best available / Okay / Low priority.
  • Retain the existing25 mass/s reference processing hypothesis for now.
  • Use the same whole-playable-area boundaries on all paths.
  • No further delay sweeps or automatic group-count selection for production work.

These constants live in strategy/reclaim_policy.py. New computations must use this policy. fixed_three_tiers ignores the historical automatic selection; exact weighted ordered breaks still determine the three groups. Fewer than three distinct qualities leave empty output tiers rather than arbitrarily assigning equal objects different quality. All11 pilot maps have three nonempty groups.

tools/build_standard_reclaim.py materializes the existing1s profile and its three-group fit without rerunning extraction, routes or sensitivity searches. It exports per-map standard_reclaim.json, root standard_policy.json and standard_reclaim_metrics.csv:11 maps,88 saved contact-budget configurations, 1716 tier rows. Existing research artifacts and their hashes remain untouched. The local viewer defaults to the single1s profile with fixed3 groups. Other options display cached research and are not instructions to compute more cases. Legacy compare/build sensitivity commands remain research-history tools; do not use them for new operating runs without an explicit research request.

Five policy tests cover fixed settings and degenerate stock. All181 targeted tests pass. Export audit verifies source hashes, exact selected-profile/model parity and all88 configurations. Browser checks confirm one1s card, locked three-tier selection, correct current-profile budget gains, no errors/overflow.

Economic comparison (initial proposal; construction-aware test now implemented)

The first test now includes construction mass/time and a separate energy ledger. See the implemented economic pilot; the proposal below records its starting rationale, not a claim that mexes operate immediately.

Compare a route's continuing mex income and finite collectable reclaim over one fixed early-game window, provisionally300 seconds:

economic_pull_p = income_p * T + collectable_reclaim_p(T)

Use actual configured T1 mex income, not marker count where income differs. Collectable reclaim follows best-first per-entity rates under the1s model and one explicit map-level engineer-work budget. Shared entities and markers are credited once through existing fractional ownership. The same budget is shared across paths; adding a contact must not manufacture engineers. Tier labels are summaries/collection priority, not arbitrary3:2:1 value multipliers. The initial collection-only proxy excludes travel and is economic opportunity, not actual match income. Mex capture/build timing and construction costs are not yet part of this proposal; they should not be silently claimed simulated.

Use the same eligible contested-resource scope on both sides of this comparison; protected base/rear stock used to calibrate tiers does not thereby enter route strength. A resource-class balance can be derived directly:

reclaim_weight = sum(collectable_reclaim) / (sum(collectable_reclaim) + T*sum(income))

Store mex pull, reclaim pull and their combined value separately. Feed this economic pull into existing distance/response logic rather than calling it army combat strength. Persistent mex pressure remains visible as reclaim depletes. The300s horizon and engineer budget are a proposed first baseline, not an additional approved settings sweep or a completed reweighting of routes. Energy remains a separate reward in a shared collection operation, with its matching source-audited time model pending; no universal mass:energy rate is set.
