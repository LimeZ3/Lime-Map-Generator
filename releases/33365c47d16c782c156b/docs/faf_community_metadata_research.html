The reviewed commentary implementation is a collection of reviews with score and text. It does not establish a separate threaded comment/reply system.

What play count actually measures

Migration V116 increments a version's count after insertion into game_stats. It has no completion, duration or rating-validity condition. A second trigger propagates the delta to the parent map. The migration backfills from distinct game IDs.

Consequently, describe this as recorded game usage, not completed matches, unique players, ranked matches, or a quality score. The same migration replaces old statistics views: plays becomes games_played, while downloads and draws become constant zero. Do not interpret those legacy zero fields as measured downloads/draws.

Concrete extraction route

Base: https://api.faforever.com; send Authorization: Bearer <access token>. The following are readable query designs, with query parameters URL-encoded by the HTTP library in implementation.

  1. Inventory maps and summaries:

    GET /data/map?include=latestVersion,latestVersion.reviewsSummary,reviewsSummary&page[size]=100&page[number]=1&sort=id

  2. Inventory all versions, rather than only latest versions:

    GET /data/mapVersion?include=map,reviewsSummary&page[size]=100&page[number]=1&sort=id

    For a targeted request, use a filter such as map.id=in=(123,456). The Rust client's summary collection uses this filter shape. Exact-folder lookup against mapVersion.folderName is also a candidate for the initial pilot.

  3. Fetch review text across versions. Client-proven route:

    GET /data/map/{mapId}/versions?include=reviews,reviews.player&page[size]=100&page[number]=1

    For bulk collection, the API model exposes root resource mapVersionReview, making this a promising alternative:

    GET /data/mapVersionReview?include=mapVersion&page[size]=100&page[number]=1&sort=id

    Validate that bulk route, relationship completeness and pagination with authenticated samples before relying on it. Reviewer profiles need not be included for our first dataset. If nested included reviews are truncated, walk the version's reviews relationship separately and reconcile counts.

  4. Follow pagination to completion, save raw responses and deduplicate by (type, id). Resolve relationships through JSON:API linkage, not matching numeric IDs alone. Use totals/next links where returned, and explicitly record incomplete requests rather than treating partial output as complete.

Start with pages of 100. Follow-up inspection resolved the apparent 100 versus 10,000 discrepancy: ElidePageSizeUtil limits ordinary users to the configured default page size (source default 100); only accounts with ROLE_SCRAPER receive the configured maximum (source default 10,000). Deployed configuration remains unverified. Do not assume a requested large page was honored. Avoid copying the client's hard page ceilings into an allegedly complete export.

Use modest sequential request pacing, retry 429/temporary failures with backoff and respect Retry-After. These are proposed collector settings, not a verified FAF rate-limit policy. Cache pages and checkpoint progress. Refresh mutable counters and periodically reconcile edited/deleted reviews; an ID-only incremental crawl misses edits and deletions.

Authentication options

The Rust client implements Authorization Code + PKCE using FAF's Hydra service, a loopback callback, an in-memory access token and OS-keyring refresh storage. See oauth.rs.

  • Preferred long-term: a standalone Python collector in MapGen with its own legitimate OAuth client registration/configuration. Verify FAF's registration process, allowed redirects and minimum read scopes before implementing login. Do not blindly copy the game client's upload/lobby scopes.
  • Practical client-assisted route: add a local JSON export command to a development build of the Rust client. Reuse its authenticated API service and export only data. This avoids needing a separate OAuth integration for the first extraction, but requires building and maintaining a client modification.
  • Optional bulk alternative: ask FAF maintainers for a research export if API collection proves costly. This is not required by the source architecture and was not requested during research.

No existing credentials or keyring entries were inspected. The unresolved prerequisite for a live pilot is an authorized authenticated session or an agreed export path.

Joining to MapGen

Our data/interim/faf_modsmaps_canonical_metadata.csv already stores map_dir, selected_map_dir, scenario name and map version. Join against all API versions using the exact versioned folder name first. Store FAF map ID and version ID alongside our existing local identity.

Do not join solely by display name or strip .vNNNN and silently assign the latest version. Case-normalized matching can be a fallback only with collision checks. Local renames, bundled variants and unpublished maps must remain unmatched or ambiguous until inspected. Produce exact/normalized/ambiguous/unmatched counts before enriching the catalog.

Suggested outputs:

  • data/raw/faf_api/<snapshot>/: raw responses and request/snapshot manifest, excluding credentials.
  • data/interim/faf_maps.jsonl: parent attributes and API summary.
  • data/interim/faf_map_versions.jsonl: exact version metadata, counts and summary.
  • data/interim/faf_map_reviews.jsonl: deduplicated review text, score and version provenance.
  • data/interim/faf_local_map_matches.csv: local map identity to FAF IDs, match method and status.

Keep map-level and version-level counts and scores in separate columns. Parent statistics must not be summed repeatedly over our local versions. Preserve missing values as null. Recompute review averages from distinct review IDs and compare with the API summaries; preserve discrepancies rather than silently replacing them.

The Rust client itself has corrective logic to sum reviews over versions when a parent summary is missing/stale: review_totals.rs. Its display-oriented 'keep whichever count is larger' rule should not become our research truth rule: counts can also decrease after deletion. Store both sources and the capture time.

How to use it in this project

This is valuable existing community evidence, but complements our structured survey rather than replacing it. Popularity measures exposure and repeated use; star ratings measure reviewer preference; comments can suggest balance, terrain or resource issues. They do not directly supply our separate gameplay-dimension labels.

Recommended first implementation milestone: authenticate, sample several known maps including an older local version, verify all three data types, then run a matching/coverage audit over the local inventory. Report how many maps have a match, play counts, any ratings and nonempty comments before deciding on training weights.

Use ratings with their sample sizes and consider shrinkage for sparse reviews. Keep popularity separate from quality, consider map age and matchmaker exposure, and preserve existing family-aware train/test splits. Review text analysis should produce provisional labels with provenance and manual validation. Keep raw review exports out of the public catalog by default; publish derived statistics deliberately rather than automatically republishing reviewer profiles/text.

Follow-up: qualifying games and responsible collection

User-defined baseline: at least two players and at least five minutes. For the stated goal of excluding solo tests, interpret players as distinct human participants, excluding AI and spectators. Validate participant representation against known games before the pilot is accepted. Keep the raw participant/AI counts for auditing. Two humans and five minutes is an operational usage definition, not proof of a competitive or completed match; do not silently add ranked-only, opposing-team, mod or victory-condition requirements.

The Rust client's replay query implementation establishes:

  • Duration uses replayTicks, at 10 simulation ticks per second: five minutes is replayTicks >= 3000. This is simulation time, not wall-clock endTime - startTime.
  • Actual player count is a local post-filter. mapVersion.maxPlayers is capacity, not actual participation; it cannot exclude a solo session on a multiplayer map.
  • Mod and victory condition have server-side filters. Player-rating filtering uses a historical mean approximation, not an exact game-average displayed rating. Preserve rating changes if exact rating analysis becomes necessary; omit that expensive relationship from the baseline usage crawl.
  • Unbounded filtered history queries can be expensive. The client normally adds a date floor. A research collector must use explicit windows and record its coverage, rather than quietly inheriting a recent-history default and labeling it all-time.

Candidate metadata-only request (requires authenticated validation):

GET /data/game
  filter=(replayTicks=ge=3000;startTime=ge="WINDOW_START";startTime=lt="WINDOW_END")
  include=mapVersion,playerStats,featuredMod
  sort=id
  page[size]=100
  page[number]=1

Use sparse fieldsets after validation to retain game ID, map-version linkage, start/end timestamps, replayTicks, validity, featured mod, victory condition, and participant identity/AI status. Count distinct human participant IDs locally, deduplicate games by game ID, and aggregate by version then parent map. Verify included participant completeness. No replay binary downloads are needed for these fields. Do not require replayAvailable=true solely for metadata analysis: that would potentially exclude otherwise usable historical records.

Save the result as qualifying_games_2humans_5min with window start/end, capture time, rules version, and collection completeness. Keep original gamesPlayed separately. Missing replay ticks are unknown duration, not zero; report that coverage separately if measured. A time-window count must not be compared as though it had the same denominator as a lifetime counter. Later-arriving replay metadata requires a trailing-window reconciliation on refresh.

Service usage findings and proposed controls

Searches of FAF sources and public guidance did not establish a published requests-per-second allowance or a guarantee against account restrictions. GitHub API rate limits are unrelated to api.faforever.com and must not be reused as FAF limits.

The API has a deliberate larger-page permission: ElidePageSizeUtil.java. This supports asking maintainers about approved research access, a SCRAPER role if appropriate, or a prepared metadata export; it does not authorize elevated access automatically.

Proposed pilot limits, pending maintainer guidance: one request at a time, at least five seconds between completed requests, at most 20 requests per explicit pilot run, 100 records per page, and an explicit short date window. These are our conservative engineering defaults, not FAF policy or proof of acceptable load. Slow queries also consume server resources even at a low request rate.

Collector requirements:

  • Dry-run request plan and hard request budget; no automatic full-history crawl.
  • Explicit date windows, checkpointing and durable caching; aggregate locally once instead of repeatedly querying counts for thousands of maps.
  • Respect Retry-After; pause the run on 429, access-denied responses, repeated server errors or severe latency. Bound transient retries within the request budget.
  • Identify the collector honestly, use legitimate OAuth access, and do not rotate accounts/IPs or bypass restrictions.
  • Avoid repeated expensive totals queries and unnecessary player profiles, rating journals or replay downloads.
  • Before a large historical backfill, obtain guidance from FAF API maintainers on window size, rate, timing and preferred export/access method. This is a recommendation based on the user's stated caution, not a discovered mandatory approval rule. No message has been sent to anyone.

Suggested maintainer inquiry (draft only): “I am working on MapGen, an open-source student research project on Supreme Commander map structure. I would like to collect map ratings/review metadata and game metadata to count games with at least two human participants and 3000 replay ticks. I do not need replay files or private account information. Is there a preferred export or API access method, and what request rate, page size and historical window would you recommend? Does this use case warrant the SCRAPER role? I can cache all responses and run a bounded, resumable collection.”
