2. Solidify the 10x10 km / 1v1 dataset

  • EXTRACT-06b — Audit and freeze an identifiable dataset release. Pending.

    Start from the existing curated cohort: **1,117 maps, 1,020 train / 97

    validation**. This is a source candidate, not a newly audited release. Give the

    next frozen dataset a display name, stable ID, version and release manifest.

    Working proposal: MapGen 10km 1v1 Core, mapgen_10km_1v1_core; assign its

    release version only when its audit/inclusion rules are frozen.

  • Publish field-level readiness and omissions. For each field and map, record

    source/version, map configuration/default resolution, representation/shape,

    units, valid domain, coverage, extraction status, semantic validation, tensor

    encoding, loader use and missing/rebuild requirements. Distinguish known-zero

    from unknown, current training inputs from future/analysis-only fields, and

    role-specific eligible subsets from the master map count. Verify boundaries,

    coordinates, physical scaling, source hashes, family splits and default 1v1

    scenario identity. A rendered preview alone does not validate a field.

  • EXTRACT-06a — Add a non-square size class. Implementation pending. Record

    native and playable width and height independently, aspect ratio, footprint

    class (square/non-square), bounds and padding validity. Non-square maps such

    as a 20x10 km playable area must not be portrayed as square terrain. Do not

    squash them or silently include them in a square 10x10 km release; representation

    and eligibility must be explicit. This is a data-domain task, not just a label.

  • **EXTRACT-05 — Calculate slope and include it where relevant alongside terrain.

    Decision accepted; implementation pending.** Candidate field: physical

    steepness 1 x 256 x 256, with world-unit spacing and neighborhood validity.

    Use it as an explicit downstream terrain-derived input where relevant, and

    consider auxiliary physical-slope supervision for the terrain model. Preserve

    height as authoritative geometry and generation-time availability: do not

    condition terrain generation on a clean target slope it cannot obtain at

    inference. The exact loss/weight and loader integration still need validation.

    The existing encoded-gradient loss is not a dedicated physical-slope target.

    Match supervision to the represented height resolution; native-only slope

    summaries are separate evidence. A separate atlas image is not the goal.

3. Dataset-wide settings, defaults and configuration variants

  • **EXTRACT-14 — Inventory settings/defaults for every map in the dataset.

    Large planned research task, not a five-atlas-map checklist.** Count declared

    options and supported values, preserve original setting IDs/names/types, locate

    choices/ranges and source code, and report parsing/dynamic unknowns. Distinguish

    lobby-declared defaults, script fallback defaults and the effective resolved

    default. Do not infer defaults from a player's last lobby selection. Authors

    use different conventions and custom logic; a name alone does not establish

    behavior. Record dependencies and the fields/entities actually affected.

  • **EXTRACT-11 — Resolve setting-dependent entities and possible training

    variants. Planned, linked to EXTRACT-14.** Determine which resources, props,

    wrecks and civilians exist under defaults and how supported option/slot choices

    change their presence or quantities. Low/medium/rich are examples, not assumed

    universal settings. A map with few resources and the same map with rich

    resources could become distinct configuration examples with their own extracted

    tensors and optional training conditions. Do not merely relabel identical arrays.

  • Keep identities separate. Original map author-version, dataset release,

    settings-variant ID and augmentation transform are different things. Variant

    identity includes source version/checksum, resolved settings and active starts.

    Every configuration/augmentation of one source family stays in the same split.

    Option counts do not establish the number of valid combinations; do not blindly

    take a Cartesian product of interacting settings. Unknown runtime behavior is

    not silently counted as the default or as zero entities.

  • Static map generation remains the model scope. Investigating source-map

    settings and later extracting configured examples does not authorize or imply

    an adaptive-map generator, configurable generated-map export or exhaustive

    configuration enumeration. Those outputs are out of current scope.

4. New appearance data: special effects

  • **EXTRACT-12a — Research and specify a separate Special effects in map appearance

    tensor. Planned; not extracted or trained.** Determine how source maps record

    effects: serialized records, markers, scripts, asset/blueprint references or

    runtime emitters. Preserve effect IDs/pool references and instance coordinates,

    plus available scale, orientation, speed and other parameters/defaults. These

    are candidate fields, not a claim that every effect stores all of them directly.

    Most maps may have no effects; distinguish verified absence from unsupported

    extraction. Keep effect instances and asset definitions separate from textures,

    resource props, gameplay scripts and sampled appearance frames.

  • EXTRACT-12b — Heatmap representation saved for later. Heatmaps are a

    candidate spatial representation. Preserve IDs and instance parameters first

    so spatial aggregation does not discard identity. Channels, animation/time

    treatment, conditioning and model role remain undecided. Do not equate a

    fixed preview frame with a completed effects tensor.

5. Deferred difficult rules and explicit scope exclusions

  • EXTRACT-09 — Access structure, hover and drop-only regions: moved to the

    difficult/explicit-rules queue. Review definitions after symmetry and scenario

    identity; unwalkable terrain is not automatically a valid landing destination.

  • EXTRACT-13 — Full battle-path continuity: hard; discuss later. Preserve

    passable connectivity, shared sections and route/contact distinctions.

  • EXTRACT-03 + EXTRACT-04 — Economy zones and contestability: hard; discuss

    later. First test improvements from symmetry enforcement. Remaining zone

    definitions/risks may still require rules; symmetry is not assumed to prove

    safety. Mex and reclaim distinctions remain part of that later discussion.

  • EXTRACT-08 — Air drop/raid scoring: very hard; deferred. Good versus bad

    opportunities require benefit/response assumptions, weighting and scoring

    decisions. No new score or calibration is approved by this plan.

  • EXTRACT-10 — Team-game scenarios: postponed. Current scope is 1v1 only.

    Retain the future 2v2/3v3/4v4/6v6 layout task without implementing or labeling

    current outputs as team-game evidence.

  • EXTRACT-02 — Specific atlas-map extraction reruns: out of current scope.

    Preserve existing missing-version/movement evidence as history; do not schedule

    Setons FAF/FAF Beetles or other particular-map jobs to fill presentation rows.

    Dataset-wide inventory/audits are not limited to those examples.

  • EXTRACT-15 — Optional artificial augmentation: low priority; keep as an

    anti-memorization option. The current terrain loader already performs random

    quarter-turn rotations/reflections; verify all relevant channels and other

    model loaders before claiming new coverage. Pixel shifts are a separate future

    option with explicit padding/cropping, coordinate/metadata transforms and

    validity/relabeling rules. Avoid toroidal wraparound and accidental resource/

    spawn loss. Apply transformations consistently to spatial data, directional

    features, symmetry descriptors and entity coordinates. They add presentations,

    not independent map families, and do not guarantee prevention of memorization.

Before another training run

  • Establish symmetry and scenario mappings, then audit the named dataset/field

    contracts. Source-only, uncertain, unsupported and planned data stay explicit.

  • Rebuild only approved affected data under a new release with tracked provenance;

    preserve historical releases and family separation, including future variants.

  • Check loaders and training receipts against actual channel roles and shapes.

    Every conditioning input must be available through the generation pipeline.

  • Record/publish readiness and review before further training. This planning

    update launches no extraction, model run, configuration expansion or automation.
