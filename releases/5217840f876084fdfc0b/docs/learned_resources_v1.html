Learned Resource Placement V1

Scope

The user-approved terrain generator is frozen. The next learned stage places mexes and hydros given terrain and two planned base locations. This is not a rule-based resource generator. Spawns remain the terrain model's input anchors for this first experiment; moving them independently would break that contract.

Reclaim/prop generation follows this stage. Texture generation is a separate last stage. Neither is trained in this pilot. No rule-based resource, reclaim, or texture replacement has been added.

Dataset

data/tensors/resources_curated_256_v1 inherits the reviewed terrain cohort:

  • 1,020 training maps, 97 held-out maps, one representative per curated family.
  • Human exclusions remain excluded; unreviewed maps remain retained.
  • Active 1v1 adaptive configurations and exact mex/hydro coordinates are reused.
  • Coordinates are rasterized directly at 256x256, not upscaled from old tensors.
  • Each marker is a Gaussian with a four-world-unit standard deviation.
  • No imposed resource symmetry, template layout, or resource snapping in targets.
  • Terrain encoding is frozen; count normalization is fitted on training maps only.
  • All packed arrays, source archives, and metadata have recorded checksums.

Terrain conditioning has seven channels: relative height, water signed distance, water depth, land passability, hover passability, and the two planned base fields. Targets have two channels: mex heatmap and hydro heatmap. Counts and water state provide three scalar conditions. There are no target resource channels in the spatial input.

Model And Pilot

supmapai.ml.resource_diffusion reuses the existing five-scale U-Net blocks in a separate model with 4,999,842 parameters. No terrain-model weights are changed. It uses velocity-prediction diffusion, foreground-weighted denoising loss for sparse peaks, joint rotations/reflections, base-channel swaps, and EMA weights.

The first run has a 600-second wall-clock budget, microbatch four, accumulation two, bfloat16, periodic validation, atomic checkpoints, and a GPU memory guard. progress.json reports elapsed/remaining time. A pause.request file asks it to checkpoint and stop. A matching --resume continues within the original budget. This is a short feasibility run, not a claim that the model is fully trained.

$env:PYTHONPATH = 'src'
.venv-codex\Scripts\python.exe -m supmapai.tensors.resources build `
  --source data\tensors\terrain_curated_20261024_v1 `
  --out data\tensors\resources_curated_256_v1

.venv\Scripts\python.exe -m supmapai.ml.resource_diffusion `
  --dataset data\tensors\resources_curated_256_v1 `
  --out data\models\resources_curated_256_pilot_v1 --seconds 600

Evaluation Before Export

The generated-terrain test uses the exact native terrain from seed 303, water 20%, without the old deterministic test resource pads. Four independent resource seeds receive the same terrain, planned bases, and requested resource counts. Four randomly selected held-out maps provide original-marker comparisons.

The diagnostic gallery shows raw heatmaps and local-maxima decoded points. There is no fallback placement, terrain repair, or forced symmetry. A missing peak stays missing. Decoding caps the number of peaks at the requested count, so matching that count is not proof that count conditioning works. An uncapped heatmap integral is also reported, with noise/overlap limitations.

Static footprint checks distinguish dry hydros from dry or submerged mexes. They are candidates only: they do not prove engine buildability or competitive balance. Held-out proximity to author positions is informative but not an absolute quality score, since several resource layouts can suit the same terrain.

Before an MVP game export, inspect: concentrated starting economy at both bases, useful expansions, count and water compatibility, symmetry enforcement effects, and the size of any validator corrections. Reject or retrain poor predictions; do not hide model failures behind a procedural replacement.

Completed Pilot Results

The initial pilot was paused at step 1,857 at the user's request, then resumed and completed at step 3,265. Total budgeted training time was approximately ten minutes, excluding the time it remained paused. Peak GPU allocation was 2.3 GB. The best EMA checkpoint is data/models/resources_curated_256_pilot_v1/best.pt.

Results gallery: data/models/resources_curated_256_results_v1/index.html. It contains four resource seeds on the approved seed-303/water-20 terrain, requesting 48 mexes and two hydros, plus four fixed randomly selected held-out maps with original-marker comparisons. These previews are not game exports.

  • Best held-out weighted velocity loss: 0.05247; this is not a gameplay score.
  • Generated-terrain static footprint candidates: 155/192 mexes (80.7%), 4/8 hydros (50%). No points were repaired or replaced to improve these numbers.
  • Mexes within 48 world units of the two bases vary from two to five per base.
  • Uncapped heatmap integrals suggest roughly 217-224 mexes and 86-96 hydros despite requests for 48 and two. Diffuse positive background and peak width affect this estimator, but count calibration is clearly not yet convincing.
  • Decoded counts equal the request only because maxima are capped at that count.
  • On the four held-out examples, mex proximity precision within eight world units is 13.5-25%; hydro precision is 0-16.7%. Other valid layouts are possible, so these are reconstruction diagnostics, not balance scores.
  • As an encoding check, original target heatmaps recovered all 2,214 resources across 24 randomly sampled held-out maps. This is not a model prediction score.
  • Thirty resource-related unit tests pass, including joint augmentation, family-leakage rejection, seeded sampling, and no fallback for flat heatmaps.

The experiment establishes a working separate learned resource stage, not a playable learned-resource MVP. Next work should compare sparse-target/loss and count-calibration alternatives, then evaluate starting economy and native footprints. Foreground-weighted denoising may contribute to overprediction; this is a hypothesis to test, not an established cause. Keep exact symmetry and bounded validator corrections explicit when exporting learned predictions. Do not claim that more compute alone will solve these issues. No training is left running after this pilot.

Sparse / Medium / Rich Comparison

Each seed uses identical initial noise across count settings. The top row changes model conditioning; the control row reuses the rich output and only changes the decoder cap. Mean uncapped heatmap-integral proxies are 148.8 / 165.6 / 220.4 respectively; these are not actual marker counts and remain far above requests. Exact decoded counts still follow from the decoder cap. Static mex footprint candidates are 83/96, 102/128, and 155/192 across the four seeds. Thirty-two resource-related tests pass.

Post-Generation Resource Symmetry

Resources now follow the terrain workflow: generate the full map first, then apply a hard symmetry constraint. No half-map model or retraining is involved.

supmapai.export.resource_symmetry supports the same five two-part raster symmetries as terrain. The current terrain uses rotate180. The default projection method is average; copy_a and copy_b are alternatives. Both resource channels use the same chosen plane and method. Water-area-preserving terrain logic is not applied to resource heatmaps.

Decoding selects whole marker pairs, not independent top-K pixels. One decoded subpixel peak and its exact world-coordinate counterpart are kept together. Coordinates use a 1/1024-world-unit binary grid so reflecting them introduces no floating-point pair error. The terrain and planned bases must already share the chosen symmetry. Close or fixed-axis pairs are rejected, not duplicated. V1 requires even mex/hydro budgets; odd budgets need future explicit fixed-point handling. Insufficient peaks yield a recorded shortfall, never rule-based fill.

The standard sampler retains raw research output by default. Enable paired symmetry explicitly for generated terrain with no asymmetric held-out examples:

$env:PYTHONPATH = 'src'
.venv\Scripts\python.exe -m supmapai.tools.sample_resources `
  --checkpoint data\models\resources_curated_256_pilot_v1\best.pt `
  --condition data\models\resources_curated_256_pilot_v1\seed303_water20_condition.npz `
  --out data\models\resources_symmetric_example `
  --mexes 32 --hydros 2 --seeds 22 --held-out 0 `
  --symmetry rotate180 --symmetry-method average

Cached comparison: data/models/resource_symmetry_v1/index.html. It includes 12 original seed/preset combinations, with raw vs average and copy alternatives. All 36 symmetric variants meet their requested counts and have zero measured world-coordinate pair error. The source arrays and terrain are unchanged; all 60 comparison PNGs decode successfully. No underwater filter or build-pad repair is introduced. Averaging retains four submerged mex occurrences across the comparison, demonstrating that underwater resources remain possible.

An end-to-end standard-sampler check for seed 22 medium produces 32 paired mexes and two paired hydros: five mexes and one hydro in each near-base ring. Only 28/32 mex footprints are static candidates, so symmetry does not replace buildability/access validation. Forty-one resource tests and six native-export tests pass. No training or game session was started for this symmetry step; the sampler check performs inference only.
