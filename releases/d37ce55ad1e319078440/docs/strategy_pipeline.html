Implemented 19 October 2026. Entry point: python -m supmapai.tools.run_strategy_pipeline. The settings file contains the operating defaults. This pipeline connects the newer shared mass economy, economic fronts and contact-response drop/air calculations without depending on the old 630-map report or named-map pilot lists.

Scope

  • Every supplied map version is a separate job. Identity uses parent ID plus version ID, source contents, settings, code and pinned dependencies. There is no latest-parent deduplication or hidden-map filter.
  • The default input is the existing latest-version download catalogue. Additional catalogues and local directory trees can include older versions. This does not download missing historical versions or retry old map downloads.
  • Native structural terrain navigation supports SCMAP 52, 53, 56 and 60 through the repaired legacy/modern reader. A corrupt or unknown format is recorded explicitly; compatibility is not achieved by silently ignoring terrain codes.
  • Default setup is 1v1, slot 1 versus a meaningful terrain-compatible counterpart. Explicit setup files can select another real pair. Maps without a meaningful default opponent are listed as excluded, without zero opportunity scores.
  • Qualified symmetry is enforced through conservative passability intersection and exactly reflected fronts. Otherwise a real two-player/explicit pair uses two independent own-half fronts; no enemy geometry is invented.
  • Land-disconnected maps still receive hover-engineer expansion and generic air analysis. Their connecting land-front stage is not applicable, rather than an extraction failure. Latest front fitting remains land-only.

Connected calculation

local version + coherent scenario/save/terrain/script family
    -> structural movement masks + actual two-slot default resources
    -> configured props / initial wrecks and numerical mass inventory
    -> fixed 1s-per-entity / three-group collection policy
    -> one shared construction/reclaim schedule before route fitting
    -> three mex/reclaim balance settings, contact budgets 1..8
    -> resource-attracted deployment, shared sections and contact territories
    -> economic value / deployment time -> normalized route-response budget
    -> physical walking from stationed contacts, base response and hover access
    -> strict / medium / permissive expansion, offensive and generic-air targets
    -> versioned JSON, numerical layers, PNGs, CSV and interactive report

One existing UEF T1 engineer shares a 300-second window across the eligible own-side land-front pool, including separately attributed Base-preferred resources. T1 mex construction costs/time and income after completion are included. A disclosed 36-mass capital advance enables the first build and is excluded from gain. Reclaim retains mass/25 + 1s work. Equal jobs share expected attribution, so task ordering does not invent asymmetric importance.

Expected collected mass and net constructed-mex returns become spatial values before optimizing contacts. Adding a contact cannot manufacture engineer work, stock or income. Allocation is recomputed on each resulting layout. Existing terrain rules, endpoint capture, exact qualified symmetry and shared approaches remain in use.

On qualified symmetric maps the selected own-side economic reference is mirrored with the geometry/response allocation. This is explicitly a normalized canonical reference, not a claim that slightly different enemy prop stock was independently fitted. Asymmetric pairs are evaluated independently on both sides.

Contact weights are proportional to allocated net mass divided by deployment travel time and sum to one route-response budget. The independent base-response strength remains available. Defending economic areas use own-half physical walks; response across the frontier to an expansion uses the full physical land graph. No point along a deployment trace becomes a free stationed army source.

Settings retained

Setting Defaults / interpretation
Reclaim versus mex balance Three multipliers 0.5 / 1 / 2 on the mex component. alpha = collected_reclaim / (collected_reclaim + multiplier * net_mex_mass). Lower multiplier favors reclaim. All use the same shared-work window.
Route-response strength 25% / 50% / 100%, plus the automatic connectivity/directness primary setting. This changes assumed suppressive capacity, not physical walking speed.
Base-response strength 50% / 100% retained from the collection sensitivity set.
Drop opportunity preset Strict / medium / permissive, with existing economic and response gates.
Contact budget 1..8 retained; default display is K4, an explicit review setting, not a claim that every map has four routes. Actual contacts may be fewer.
Reclaim policy 1s acquisition per entity, three map-relative groups, 25 mass/s processing hypothesis. No new delay or group-count sweeps.

The balance names early/context/late remain artifact identifiers for the three existing settings. In this pipeline their numeric factors adjust the balance of the two finite-window mass returns; they do not run three different engineer schedules or add independent work budgets. All values/settings are exported.

The configuration file retains the three tunable balance factors and response strength lists. Changing them creates a different run identity. There is no automatic search for values that reproduce known player rankings.

Energy is ignored for scoring. It cannot change collection order, economic return, route attraction, response weights or target flags. Source energy fields can remain in the reused entity extraction, but no energy-tier, power-stall or mass-to-energy optimization runs. Hydros remain identifiable spatial markers; their energy return is not monetized.

Important interpretation limits

The shared schedule is a feasible mass-return approximation, not optimal play. It omits travel, worker production, upgrades, existing base income, combat and storage constraints. The independent base and route strengths remain hypotheses about available defenders; AA and intel are unknown.

The calibrated drop reward screen still uses the existing T1 mex saved-income / income-denial proxy. The new mass economy changes front placement and response allocation. It does not pretend that gunships can damage initial rock mass, or that the drop's complete construction/financing/combat ROI is simulated. Regions also export known reclaim and unresolved counts for later interpretation.

Generic air raids include underwater mexes through torpedo aircraft, using the agreed representative gunship economics. Numerical naval firing potential is not recomputed here; naval support and scripted wall/dynamic hazard collision remain explicit limitations. No universal independent-route count or new 1–5 gameplay rating is inferred.

Running

From the workspace, using the existing runtime:

$env:PYTHONPATH='src'

# Freeze a full-library plan and report without starting computation.
.venv-codex/Scripts/python.exe -m supmapai.tools.run_strategy_pipeline --plan --config configs/strategy_pipeline_mass_v1.json

# Run that selection. The same inputs/settings/code resolve to the same run.
.venv-codex/Scripts/python.exe -m supmapai.tools.run_strategy_pipeline --config configs/strategy_pipeline_mass_v1.json --workers 2

# Inspect progress; no process-inspection permission is required.
.venv-codex/Scripts/python.exe -m supmapai.tools.run_strategy_pipeline --status

# Resume a particular saved run using its printed path.
.venv-codex/Scripts/python.exe -m supmapai.tools.run_strategy_pipeline --run-dir data/processed/strategy_pipeline/v1.0.0/RUN_ID --workers 2

# Regenerate report tables or independently audit completed artifacts.
.venv-codex/Scripts/python.exe -m supmapai.tools.run_strategy_pipeline --report --run-dir data/processed/strategy_pipeline/v1.0.0/RUN_ID
.venv-codex/Scripts/python.exe -m supmapai.tools.audit_strategy_pipeline --run-dir data/processed/strategy_pipeline/v1.0.0/RUN_ID

Add repeated --key MAP_ID_VERSION_ID arguments for a smoke cohort, or --limit N for a bounded run. Repeated --catalog path.csv arguments combine compatible catalogues without collapsing versions. --maps-root path recursively discovers local map folders and assigns stable local identities. It can be repeated and combined with catalogues; directory discovery does not identify those folders as official FAF IDs. Do not include the same physical map through both input methods unless separate identities are intentional.

Compatible catalogue rows use map_id, version_id, display_name, folder_name, local_path and JSON path arrays scmap_paths, scenario_paths, save_paths, script_paths. Conflicting locations for one official version are rejected. Coherent scenario-family selection handles bundled backup files.

For an explicit pair, use --setups setups.json:

{"maps":{"MAP_ID_VERSION_ID":{"active_slots":[1,2],"evidence":"Reviewed intended 1v1 pairing"}}}

The slots must really exist. A setup is tied to the versioned run; it does not silently reinterpret older results.

Resuming, limits and progress

  • run.json freezes selection, settings, dependencies and code fingerprints. latest_run.json points to the most recently prepared run.
  • Each version has independently sealed navigation, configured extraction, economic-front and opportunity stages. Economy/schedule evidence is included in the economic-front stage. Source, auxiliary Lua, map-local blueprint, settings and dependency changes invalidate affected saved work.
  • Every consumed numerical artifact has an output hash. Cache validation follows nested stage manifests and detects a modified/deleted array, not only changed metadata. Source hashes are rechecked before committing completed output.
  • An OS controller lease prevents duplicate controllers. Worker-slot and per-map leases survive controller interruption until existing workers finish and are automatically released on process exit. A resumed controller waits for orphan workers instead of overlapping them; it does not infer death from denied PID inspection.
  • status.json reports controller heartbeat, queue, checked count and active stages. Workers also write independent five-second heartbeat.json files during long calculations. A fresh heartbeat means active processing; a stage name need not change every few seconds.
  • Jobs run in isolated processes, normally two at a time, with a 1,200-second timeout. A conservative per-job memory estimate defaults to a 6 GiB ceiling. Resource-budget deferral is explicit, rather than silently reducing resolution. Larger supported inputs can use a materially larger --memory-gb budget and --timeout when the machine can provide it.
  • --retry-failed is explicit; routine resume does not continually retry failures. Changed code/settings create a new reproducible plan rather than overwriting an older algorithm's report. The pipeline has no replay/API/download operation.

Each completed job stores result.json, navigation/, configured extraction/, fronts/fronts.json.gz, primary territory PNG/NPZ files, and opportunities/opportunities.json.gz, numerical layers and RGB-encoded target-area PNG. Per-scenario exports retain the three balances, all contact budgets, response strengths and presets. Primary evaluations retain rejection checks; alternate strengths retain scores and per-side target IDs.

Repeated scenario and entity records use deterministic gzip-compressed JSON. The browser decompresses them locally. Python consumers can use json.loads(gzip.decompress(path.read_bytes())). Pipeline extraction skips unused pilot renders and gradient tensors; it retains configured entity identities/values, reclaim arrays, markers and provenance. Existing annotation assets remain their own library, and the pipeline produces its native terrain/target/territory previews.

The run root contains index.html, report.json, report.md, metrics.csv, status.json and, after auditing, validation.json. The CSV is the primary balanced/K4/medium view; the full parameter combinations remain per-version JSON. Reports distinguish completed, excluded, failed and pending versions. Unknown mass is a lower bound, not zero; failed/excluded jobs do not receive fake scores.

Validation

The new unit cases cover version retention, hidden entries, nested-cache corruption, exclusive leases, legacy structural navigation, opponent selection, asymmetric and reclaim-only fronts, shared mass conservation, ignored-energy invariance and the distinction between stationed contacts and deployment pixels. The extraction and strategy regression suite passed 256 tests after integration.

Real-map validation uses Astro, Seton's, Drunken Beetles, Morning Prayer, DualGap, Adaptive Tabula Rasa and Pandemonium Pass.
