Featured-map gameplay analysis plan

Prepared 14 October 2026. Scope: all maps on the signed-in featured list, not just 10×10 or 1v1. The live list has 33 maps; all 33 exact linked versions match our local catalog and have overlays. The frozen cohort is data/manifests/featured_strategy_20261014.json.

The goal is to calculate gameplay opportunities, threats and defense requirements from map geometry and versioned FAF mechanics. Outputs must say which game setup, faction, unit/weapon and economy scenario they describe. Keep raw measurements alongside derived indices so a community member can inspect the reasoning.

Shared contract

  • Pin map/version IDs, source hashes, FAF balance revision, navigation revision, profile definitions and algorithm/threshold versions. Metrics and overlays must derive from the same masks; avoid separate stale numerical catalogs.
  • Record active spawn IDs, allied/enemy teams, player count and default adaptive settings. Scenario army lists alone do not establish the intended teams. Build one verified recommended setup first for each map; add other setups later.
  • Include every featured map, including unranked featured entries. Size and ranked status remain attributes. Team/FFA configurations remain distinct analyses.
  • Keep default adaptive settings in scope. Resolve the resources actually enabled by that default/setup; do not silently use all possible static markers. Where unsupported, publish geometry and explicitly unresolved resource-dependent fields, not zero or an invented default. No adaptive-options UI is required.
  • Preserve full-map coordinates and playable bounds, raw terrain/water tensors, exact entity/resource identities, numerical reclaim, and region masks.
  • Start with current standard FAF without specialty mods or enhancements. Use the requested representative UEF units for estimates, recording the exact proxy and selected weapon. Do not enumerate every faction/unit against every mex or combine fields from different units into a fictitious profile.
  • Export measurements in game-world units and seconds; map kilometres are display units. Normalize percentages per relevant player/team as well as map.

Step 1 — Navigation and game-mechanics foundation

Integrate the pinned community map/navigation library behind a small local batch adapter. Retain our tensor/PNG/reclaim packaging and format-52 fallback. Produce terrain-driven land, amphibious, hover and naval grids, connected-region IDs and resource-to-region associations. Preserve both raw passability and the compressed, culled FAF AI-navigation view: they answer different questions.

Keep the requested 0.75 height threshold and amphibious depth limit of 25. Match FAF's four-corner, strict boundary test rather than smoothed cell gradients. Use one generic naval-depth rule initially; separate T1/T2 naval-depth boundaries remain out of scope as previously agreed. Record blocking terrain types. Add a separate initial-obstruction layer where blueprint footprints/collision behavior are known; identify reclaimable obstacles and unknown collisions explicitly.

Create versioned unit profiles from resolved game blueprints: unit ID, faction, tech/role, movement layer, speed, footprint, build cost/time, health, transport properties and relevant weapon range/target layers/damage/shot timing. Our current reclaim blueprint cache alone is not enough. Apply base-game + FAF modifications and postprocessing, or obtain an engine-exported resolved snapshot. Preserve unresolved script-dependent behavior rather than presenting raw fields as final.

Deliverable: balance_profiles.json, region grids, pairwise reachability and distance fields for each verified setup. Test flat dry ground, threshold cliffs, blocked terrain, shoreline, underwater cliffs/depth 25 and cropped map bounds. Start on representative featured maps before running all 33.

Step 2 — Naval attack reach: first gameplay feature

Use only the UEF T1 frigate (ues0103, main gun, range 28), UEF T2 destroyer (ues0201, one representative main turret, range 60), and UEF T2 cruiser (ues0202, cruise missiles only, minimum 20/maximum 150). These are sufficient proxies for the present estimates; do not extend target enumeration to other factions or T3 without a new request. Reuse launch calculations and target reach for spawns sharing the same basin set. Submarine, anti-air and cruiser gun weapons do not contribute to these selected profiles.

For resource site m and unit profile u, find navigable firing positions p in a naval region reachable from that player's viable launch locations. A potential hit requires compatible target layers/categories and MinRadius(u) <= distance(p, m) <= MaxRadius(u). Use the game's range/elevation conventions. A circular radius around all water is insufficient: a tiny isolated lake or a basin without valid factory/launch space must not create naval reach.

Add terrain/line-of-fire checks appropriate to the weapon. Keep initial range-only reach separate from terrain-screened reach, and mark trajectory behavior pending engine validation. Direct-fire, high-arc artillery and guided missiles require different treatment. Do not count range-only hits as confirmed damage.

Measurements: reachable naval basins, usable launch sites, targetable mex and hydro counts/percentages, affected expansion clusters, nearest firing positions, travel distance/time from launch, target IDs and weapon IDs. Keep per-unit values and explicit faction/tier unions; report each target once in a union. Add scenarios for T1/T2/T3 mex structures so income/build value exposed can be compared.

Preview: naval reach overlay with threatened resources, firing-location witnesses and unreachable basins. Acceptance: sample both hit/non-hit cases in game, including a cliff-screened target, island target, isolated basin and minimum-range case. The first visible milestone is a trustworthy T1-frigate mex coverage report, not a universal navy score.

Step 3 — Attack routes and obstacles

For each opposing spawn/team pair and movement profile, calculate shortest travel distances and route geometry. Build a corridor graph from navigable space, clearance fields, junctions and bottlenecks. Attach obstacle reasons: cliff, water/depth, terrain-type blocking, playable boundary or known placed obstruction.

Do not count every grid path as a different attack route. Group paths that use the same corridor/shared choke. Measure distinct approaches and route alternatives across versioned cost-stretch, separation and minimum-clearance thresholds. Record sensitivity curves rather than hiding all definitions in one route count.

Measurements: direct-vs-walking detour, route length/time, minimum/median width, shared chokepoints, independent corridors, distinct base-approach sectors, alternate-route extra time, distance to resource clusters and routes opened by removing reclaimable obstructions. Our older path/width features can be retained after replacing their underlying navigation and validating their definitions.

Preview: numbered corridors with widths, obstacles and shared bottlenecks. Acceptance: distinguish one winding choke from two independent approaches; an open plain must not generate hundreds of nominal routes. These quantities describe split-army/control pressure; a universal player-skill score is not needed.

Step 4 — Expansion drops and offensive drops

Keep two analyses separate.

Expansion access: count land-unreachable regions from each active start and their mexes, hydros, reclaim and usable landing/build area. Also test actual engineer, hover and amphibious profiles so a merely land-isolated island is not automatically called transport-only. Include naval-access status separately. Calculate engineer walking/alternative-mode travel versus transport flight, load/unload assumptions, cargo compatibility and capacity for a chosen transport.

Offensive access: establish a reproducible baseline front from competing travel-time fields and the main route corridors. This is a reference deployment, not a claim about where a real army stands during a match. Measure enemy economy behind that front, off-corridor distances, landing space, and the time for a main force or separately positioned defense to reach each target cluster.

Measurements: resources in isolated regions, mode-specific access, flight advantage, drop-compatible landing clusters, off-main-route economic value, target-to-front/main-army travel times and extra defense clusters needed under stated response-time budgets. Produce results for several army staging/reference positions instead of assuming one universal frontline.

Acceptance: a resource-free island should not receive high economic drop value; a hover-accessible region must differ from a transport-required one. Review known behind-front targets with community members and validate transport placement.

Step 5 — Air advantage and AA defense burden

Calculate attack flight paths/times, ground reinforcement times and isolated economy clusters. Map size is an input; resource placement and ground detours explain the effect. Use faction/tier aircraft profiles and stated launch positions.

Model defensive coverage using actual mobile/static AA profiles: valid placement, weapon coverage, movement time and mass/energy/build-time cost. First calculate a coverage-placement problem for economy sites, including separate clusters. Then add capacity under a defined aircraft count, health, speed and attack pattern: being inside an AA circle is not proof of surviving a strike.

Measurements: distant-mex counts, defended area/cluster count, air-vs-ground arrival-time difference, response deficits, AA placements and reinforcement time, estimated mass/energy required for defined coverage, and vulnerable mex count/value under fixed defense budgets. Mark whether coverage optimization is exact or an approximation; a greedy cover is a feasible cost bound, not the true minimum.

Preview: economy clusters, strike travel fields and example AA placements. Acceptance: clustered sites can share defenses; widely separated sites should require additional coverage. Compare terrain-detour cases, not size alone, and test selected strike/defense profiles in game.

Step 6 — Tech-stage pressure and economic safety

Reuse movement, firing reach, routes and defense coverage with representative T1/T2/T3 land/naval/air attack profiles. Preserve direct-fire versus artillery, sniper or missile roles. Include normal FAF faction differences and record any mode-dependent unit behavior in the profile rather than silently changing it.

Define explicit economy/attack/defense scenarios. Resource sites are not evidence of actual built/upgraded mexes; evaluate target structures at stated tiers. Calculate potential production using pinned mex production/upgrade costs, hydro/energy options, accessible reclaim and stated build capacity. Initial reclaim access combines value with travel/collection assumptions, not radius alone.

Measurements: vulnerable target counts/value by attacker and target tier, nominal damage and time-to-kill, earliest travel/engagement times, coverage gained from a tech upgrade, safe/contested resource access, defense/reinforcement costs, and economic investment/payback under the defined scenario. Weapon timing must respect game ticks, salvos, beams and relevant script changes; do not assume Damage * RateOfFire is universally correct.

Publish threat/defense curves over budgets and profiles. They let us describe which economy a map permits a chosen defense to protect, and what each tech stage can threaten. They do not assert that every player reaches T2 at one predicted minute. Actual tech timing remains conditional on the recorded strategy scenario.

Acceptance: use controlled unit-vs-mex tests for damage/kill time and selected upgrade/defense scenarios for economy calculations. Keep geometry-only results separate from those that need damage/trajectory/economy validation.

Step 7 — Biomes and texture composition

Read structured terrain strata, diffuse/normal paths, tiling scales, shader, stratum masks, decals and relevant water/lighting fields. Separate terrain albedo from normal maps, decals and effect assets so file references do not become a misleading terrain-texture count.

Build a canonical texture-to-biome catalog from FAF editor group definitions and FAF/game environment assets. Normalize aliases. Record custom/unknown textures explicitly and allow mixed biomes; do not infer the whole map from its first /env/ path. Retain asset provenance and map license metadata.

Measurements: unique referenced/actually used diffuse textures, normal/decal counts, area per material and biome, dominant biome, biome mixture, texture scale distribution, and texture use around water, cliffs and bases. Decode mask weights using the map's shader semantics, including implicit base strata; a loaded texture with zero visible weight is not a used design element. Custom shaders can have unknown area weights even if their texture paths are known.

Acceptance: compare the layer list and dominant/mixed biome against the map editor and representative game visuals. This module can be implemented earlier because it does not depend on combat calculations; its agreed scope remains asset composition rather than inferring beauty from texture counts.

Storage, review and progression

Use a map/configuration record plus separate unit profiles. Suggested outputs:

  • cohort.json: exact featured versions and source/configuration provenance.
  • balance_profiles.json: versioned unit, weapon and structure profiles.
  • regions.npz / distance_fields.npz: registered labels and distances.
  • resource_analysis.parquet: one resource identity with mode access, threat, region and ownership/configuration evidence; CSV export for manual inspection.
  • routes.json: corridor graph, pair/profile results and obstacle explanations.
  • map_metrics.csv: geometry, biome and configuration-independent summaries.
  • scenario_metrics.csv: map × setup × faction/profile × budget/tier summaries.
  • feature_manifest.json: definitions, units, inputs, validity flags and previews.

Every strategic summary should expose its target/region IDs and a spatial witness (route, firing position, landing cluster or defense placement). Unknown values stay unknown. Build a short per-map visual report with our existing vault preview and registered overlays; keep new previews locally until an explicit release.

Progress one module at a time. For each: implement on 2–3 representative featured maps, run boundary/consistency tests, review overlays, check disputed cases in game, then calculate all 33. Prefer concrete tests such as same-profile extra weapon reach not losing targets, removal of an obstacle not removing terrain reachability, and unchanged masks producing identical metrics and overlays. Document accepted deviations from the game and keep algorithm versions.

The first implementation batch is scope/configuration manifest + balance profiles + validated navigation, followed by T1 frigate target coverage. This is the planning deliverable; no extraction integration, bulk rerender, questionnaire rewrite or deployment has been performed for this plan.
