Atlas publication and maintenance

The atlas under docs/model-atlas is the project's main source of truth. The public address is https://mapgen-project-atlas.elven-bowl-7506.chatgpt.site . ChatGPT Sites hosts the portal; the codex/atlas-live branch of the project GitHub repository holds immutable, sanitized public snapshots and latest.json. The portal checks that pointer every 60 seconds while open, on returning to the tab, or when Check updates is pressed. It has a bundled initial fallback. It never reads uncommitted desktop files or infers progress from a running process.

Record and publish meaningful progress

  1. Update the atlas catalog/control registry, method/work notes and docs/map-extraction-todos.md as appropriate. Preserve exact checkpoint and map identities; record completed, active, experimental and planned separately.
  2. Refresh the offline model reference using project GPU Python, metadata only: $env:PYTHONPATH='src'; .venv/Scripts/python.exe -m supmapai.tools.build_model_atlas.
  3. Run node tools/refresh_project_status.mjs to refresh the structured progress page and dated GitHub report from atlas receipts and saved supervisor states. Check wording before publication, especially a running/paused/completed state.
  4. Run node tools/publish_project_atlas.mjs --push. This builds a public snapshot and pushes only the dedicated codex/atlas-live publication branch. It does not stage or commit the research checkout or modify main. Git write access is required; failures must not be reported as published. Verify the remote pointer after a push. No Site deployment is needed for a data/content update.
  5. Commit reviewed source documentation/progress changes to the research branch through the normal GitHub workflow. Keep a dated report as history; the current atlas status is authoritative. Update the local offline reference too.

A content publisher must run after meaningful recorded progress. The minute browser check does not itself turn local edits into public updates. This workflow is agent-driven/event-driven publication, not an unattended training monitor, and creates no recurring tasks or Netlify deployment.

The Datasets → 1x1, 10km audit is rebuilt from the exact local reviewer cohort using the steps in dataset-atlas.md after relevant source or processing changes. UI-only and shared review changes do not require rerendering the dataset. Keep the original audit population distinct from current curated role memberships.

Public packaging boundaries

The publisher includes reviewed atlas images/scripts, rendered project notes and selected small source/evidence snapshots. It scrubs machine-specific absolute paths. It excludes checkpoints, full raw tensor archives, private response exports, portfolio drafts and local review applications; links become explanatory evidence pages rather than broken file URLs. It must never upload credentials or expand an excluded artifact merely because a document links to it.

A public snapshot has a content digest, immutable release directory, recorded source timestamp and per-file hashes. The version pointer advances only after its snapshot is uploaded in the same Git push. GitHub retains prior versions. The Site portal embeds only this fixed project's owner-published source; it does not allow arbitrary remote document origins.

Portal/code updates

Site identity is in sites/mapgen-project-atlas/.openai/hosting.json. Reuse it. Use the Sites skill's source helper and native save/deploy workflow for changes to the portal itself, preserving public access. Do not deploy to Netlify. Source credentials belong only in session memory/stdin. The initial bundled fallback is packaged under sites/mapgen-project-atlas/public; newer content comes from GitHub.

Shared review flags

Every atlas page and heading has a human review flag: unflagged, complete, needs some work, or far from done. The Review flags page gathers the flagged sections and exports their public JSON. These judgements are independent of scientific validation, training receipts and extraction TODO completion.

The Site's /api/review-flags stores flags in its D1 database. Public visitors can read them; only the project owner can write after Sign in with ChatGPT. The initial owner must match the private ATLAS_OWNER_EMAIL environment value from trusted Site ownership, then the Site-scoped authenticated user ID is pinned. Never replace this with first-visitor registration or a browser secret. No owner identity or email is returned by the public API. Cross-origin writes are rejected, and version checks prevent concurrent tabs overwriting changes.

Flags survive atlas content publications and Site deployments. Changes appear immediately in the editing tab; other open tabs refresh within a minute or on returning to the tab. Local offline atlas files show shared flags read only. The local preview uses the supplied test identity and a separate local database; test flags must never be imported into the production database.

Dataset inclusion decisions and manual symmetry suggestions use /api/dataset-curation and the same pinned owner authorization. The schema and membership contract live in the existing Site source. Defaults keep every map except the 50 original local exclusions. Server-side validation binds edits to the exact cohort and caps a page batch at 24 maps. One guarded atomic statement prevents partial writes on stale versions. The selection export is the current shared curation receipt; rebuilding an atlas snapshot does not reset these edits.

Section notes use the same owner-only write access and public visibility as flags. Expand Notes beside a flag, type up to 10,000 characters, then Save notes. Notes are plain text and are included in the review list and JSON export even when the section is unflagged. Refreshing shared data preserves unsaved drafts in the open page. A stale-version conflict retains the draft and requires another explicit save after reviewing the latest state. Older flag-only clients preserve notes.

Keep review keys stable when renaming sections: page keys are page:<route>, layer keys use their existing layer-* IDs, other section keys derive from the route and heading. If a heading is renamed, migrate its saved key deliberately rather than silently treating its old flag as a judgement of the new section.

The Markdown renderer uses the bundled marked dependency. Set ATLAS_MARKED_MODULE to its absolute module path when a runtime bundle moves.
